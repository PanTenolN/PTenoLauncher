## Implemented local workflow

- `ModUpdateManager` identifies actual root JARs through Modrinth's SHA-512 lookup, checks the returned file size/hash, and keeps project/version/file identities separate from local names and Mod IDs. SHA-512 is the provider file identity; no fictitious numeric Modrinth file ID is invented. Unidentified local JARs retain local path/size/SHA-256/SHA-512 identity and can be pinned without assigning a provider.
- Check uses provider publication timestamps, not display-version string comparison or commit hashes. Default candidates are compatible releases with a strictly later publication timestamp; beta/alpha require explicit opt-in. A timestamp tie is ordered by stable version ID only for determinism, never to infer a newer publication. Unselected installed projects prefer their current version. Exact required dependencies can propose a replacement; persistent pins become exact constraints. Optional metadata remains visible in the plan and is not silently installed. Unknown/untracked files are retained. There is no automatic orphan removal.
- Explicit selected direct updates and explicit removal of known, owned provider files feed dependency resolution. Preview distinguishes Update, DependencyAdd, DependencyReplace and Remove. The saved plan contains exact versions, provider filenames/URLs, hashes/sizes, the full before/after root set, inventory/pins/epoch bytes, exact profile and receipt/Quilt-overrides context. Selection changes invalidate confirmation. A changed profile, file, inventory, pin or context invalidates apply.
- All new files are downloaded into the existing hash-verified cache before profile mutation. The entire resulting physical JAR set is statically reviewed, excluding replaced old files. Existing Fabric dependency checks and bounded native Quilt/Forge/NeoForge selection are reused. Unsupported metadata or non-confirmed native selection blocks the transaction. No JAR is executed, and inner libraries are not copied into mods/.
- Persistent profile `mod-pins.json` survives restart. Pin/unpin requires explicit confirmation. Changed/missing pinned bytes are diagnosed in installed readiness, are never automatically adopted, and can be explicitly unpinned. Existing add-only `ModInventoryStore.RecordCommittedAsync` still refuses changed bytes at an owned path. The new transaction adapter does not weaken that invariant.
- Apply acquires the existing profile lease and checks world/process locks. A unique verified ZIP under `backups/` stores the complete previous root JAR set and exact metadata state, and is registered as a profile backup. It is not described as a gameplay-tested configuration. Per-operation new/old staging, `transactions/mod-update.json` and immutable operation records preserve a recoverable state across failures. Old files are moved aside, not overwritten/deleted. Metadata writes reject unrecognized newer bytes.
- Recovery requires confirmation. Prepared transactions restore the verified before state only after preflighting all files/metadata; committed journals finalize only against the exact after state. User changes and unsafe paths/links are preserved and block automatic recovery. Pending update journals block legacy imports/baseline/recovery and installed readiness. Cancellation after preparation leaves an explicit recovery path, never a success status.
- Rollback has its own preview, confirmation, backup and journal. It requires the complete original backup and exact current after state, rechecks both at apply, restores files/inventory/pins and assigns a fresh operation epoch. User changes, pins or subsequent operations refuse stale rollback; the fresh epoch also prevents an ABA rollback after returning to old bytes. Offline rollback uses no provider requests.
- Mods UI exposes check, prerelease policy, change selection, explicit known removal, preview, pin/unpin, confirmation/apply, history, rollback preview and recovery. The panel remains inside the existing Mods page, hidden for Vanilla. New labels/diagnostic templates are in all eight language catalogs (292 matching keys). AI remains optional and is off in the UI workflow test.

## Limits and known boundaries

- Supported provider: Modrinth only. Existing profiles/inventories require no migration. Untracked files can stay unchanged and be pinned; replacing/removing a tracked file requires the existing explicit integrity baseline. Unknown local JARs are not assigned provider projects from filenames or Mod IDs.
- At most 128 root JARs, 512 MiB per JAR, 8 GiB total and 8192 directory entries; nested parsing/selection retains its tighter existing bounds. Subdirectories, links, pending imports, ambiguous layouts, unsupported dependency rules and failed native selection are blocked. These are static metadata checks, not an antivirus verdict or a universal compatibility guarantee.
- Check/preview are allowed to fetch metadata; preview also fills the verified artifact cache so actual JAR compatibility can be shown. No profile changes occur before confirmation. Cached metadata reports its oldest fetch time and limited freshness; a cold offline cache says unavailable/incomplete, never no updates. No paid API, API key, AI or account is required.
- Staging and backups are retained after failures for review. No automatic backup/cache pruning is implemented. A failed pre-journal preparation may leave an unused unique backup/staging operation; recalculate preview rather than overwriting it. Concurrent third-party edits are rechecked, but this is not OS-level isolation from a malicious same-user process or a guarantee against all power/storage failures.
- Whole-game backups and mod-operation backups serve different purposes. Mod-operation ZIPs contain only root mod files and associated inventory/pin/epoch metadata; they do not copy worlds or account secrets. Normal profile deletion preserves registered backups; explicit all-data deletion can include them under the existing ownership policy.
- Technical diagnostics inherited from dependency/native parsers still have partial localization. Linguistic/native DPI/manual review remains separate. Real update/gameplay success is not inferred from tests.
